# C34 — accepted consumer publication and stale cursors

Checkout: `codex/api040-numerical-bodies` (isolated). Baseline red witness used exact carriers and two actual NPZ publications: `2 passed, 1 xfailed`; `--runxfail -k conflicting` failed at `committed_samples == 2` (actual `1`). The fixed source tests, including the independent adversarial suite, now pass `18/18` with `pops-api040-bodies`; no native extension or build was needed.

## Established guarantees

`ConsumerTransaction.__init__` authenticates exact `EffectPlan`/cursor/publisher carriers and rejects a plan whose `cursor_before` differs from its *supplied* `ConsumerCursorSet` (`_consumer_transaction.py:217–231`). Its `accept` validates publication receipts, rolls back failed publications, and advances only successfully published effects (`:396–456`). `ConsumerGraph` rejects duplicate consumer handles (`_consumer_contracts.py:732–749`). `RuntimeInstance._moments` creates one moment per clock; `_stage_consumers` plans every clock from a common accepted cursor set (`_runtime_instance.py:990–1063`). Since each manifest has one schedule clock and one graph node, those same-step plans have disjoint consumer IDs. The real-NPZ disjoint witness passes and retains both artifacts and both cursors.

## Conflicting roots and classification

Two separately prepared, exact `EffectPlan`/`ConsumerTransaction` values for the same consumer can both authenticate against the same initial cursor. Their real NPZ publications both succeed; replaying each accepted `cursor_updates` through `ConsumerCursorSet.replace` leaves one committed sample instead of two. The second transaction does not compare against the *current* cursor at acceptance. This is a reproducible **IMPL** limitation at the standalone transaction seam (`_consumer_transaction.py:217–231, 396–456`; `_consumer_contracts.py:1024–1030`). A plan constructed *after* the first acceptance using the advanced cursor is rejected, as the third witness confirms.

It is **SCOPE**, not a confirmed ordinary `RuntimeInstance` lost update: the current graph/clock routing excludes a duplicate consumer across one call to `_stage_consumers`, and the runtime accepts its staged transactions serially (`_runtime_instance.py:1143–1155`). The witness deliberately constructs two valid transactions independently, a composition that the low-level API permits but the ordinary step controller does not currently produce. No native C++ publication flaw or asynchronous branch was inferred from this test.

There is no **EXPR** finding: manifests, schedules and source expression ownership were not mutated. There is no **MATH** finding: the loss concerns accepted publication metadata, not a numerical update. A stale *scientific data read* is not demonstrated: this witness varies cursor authority, not state readsets, and this transaction API has no state-readset/version argument to test that property.

## Bounded correction at the publication seam

Implemented `ConsumerCursorAuthority` as a required, execution-only authority for `ConsumerTransaction`; no durable payload/schema changed. It reserves all write cursor IDs atomically after staging and before the first `publish`, compares the authored `cursor_before` against the current value, and rejects stale/conflicting roots before any new NPZ becomes visible. Accepted commits merge only touched cursor IDs. A reservation persists until `seal` or successful compensation, so rollback restores only that root's cursors and cannot overwrite an interleaved disjoint publication. `reset` advances an execution incarnation and invalidates staged roots even when the restored cursor values equal the old values. RuntimeInstance now owns one authority, stages against its current snapshot, and retains disjoint accepted cursors/reports when a failing step envelope is restored. Explicit checkpoint restore uses an atomic revision snapshot and compare-and-swap before replacing cursors; rollback cannot overwrite a later disjoint commit. All productive constructor call sites were migrated; the old three-argument constructor fails rather than creating a private authority silently.

Independent tests cover two competing threads (one visible winner), stale prepared roots, disjoint interleaving and rollback, a real NPZ failure followed by retry, partial publication failure with cleanup, controller envelope restoration, checkpoint compare-and-swap, and incarnation reset. If artifact compensation itself fails, that consumer enters an explicit terminal state in this runtime incarnation: further roots and cursor reset refuse with instructions to recover artifacts and recreate `RuntimeInstance`. Other consumers may proceed. No recovery-to-authority rearming API was invented. This is not evidence that asynchronous PDE steps or MPI roots are already supported. Direct manual `RuntimeInstance.checkpoint(path)` remains outside this concurrent-root qualification; state-resource readsets remain outside this cursor protocol.
