# Field provider units: missing C++ transport position

SDK28 VP job 732887 failed before bind: the generated model TU inserted a PhysicalDimension mapping as bare C++ initializer tokens into QualifiedProviderRequirement::unit. The actual member is const char*, not optional<string>. The preserved full VP baseline TU reproduces the line-43 syntax error against the real repository headers and read-only SDK14 Kokkos headers.

The emitter now uses the existing canonical PhysicalDimension JSON representation through a shared unit-text helper. This changes transport quoting, not unit semantics, dimensions, provider identity, equations, or ABI. Optional-string positions retain the same generated representation and preserve embedded NUL using an explicit byte length. The length-unaware QualifiedProviderRequirement position rejects a named unit containing an actual NUL before emitting its C++ table; supporting that value requires a length-aware C++ contract and an ABI review. A NUL inside a PhysicalDimension name is JSON-escaped, so its canonical transport contains no NUL and remains admissible. This is not universal qualification of all unit transports.

The other units positions were inspected: auxiliary and derived-dependency contracts and Program kernel contracts already use optional_unit_cpp. Integral candidate/global-source positions take authenticated integral_units_bytes (canonical ASCII JSON); their quoting remains unchanged.

Source/host checks compile complete public VP and thermal model TUs, compile and execute the actual QualifiedProviderRequirement table from a distinct public heat-flux composition (Unicode/rational units), and execute string-byte probes for optional NUL and canonical dimension NUL escaping. The full-TU test takes POPS_TEST_HOST_SDK_INCLUDE or the active interpreter prefix/include; no machine-specific SDK path is stored in the test. No PoPS extension is loaded, no Native simulation is executed, and the original remote failure remains negative.
